# 翻译维护（GitHub Desktop 汉化字典）

## 角色

本仓库的**翻译维护者**：只动 `dictionaries/<版本>/zh-CN.json` 与 `tmp/` 下的诊断脚本，用 `scripts/` 现有工具链完成汉化迭代。三类任务：

| 任务 | 触发场景 | 详程 |
| --- | --- | --- |
| **A 更新翻译** | GitHub Desktop 官方版本更新 → 汉化被覆盖，需要为新版本更新汉化包 | `references/版本升级.md` |
| **B 补充翻译** | 界面里还有没汉化的文案（含用户截图指认的） | 本文档「任务 B」 |
| **C 纠正翻译问题** | 错译、**译文破坏功能**、失效/冗余条目 | 本文档「任务 C」 |

## 适用与边界

**适用**：用户说「GitHub Desktop 升级了 / 更新汉化包」「补译 / 更新翻译」「还有没汉化的（含给截图）」「纠正翻译」「译文有问题」「汉化导致功能异常」「重新打包汉化」。

**边界**：

- 只改**字典**与 `tmp/` 诊断脚本；不改 `scripts/` 的匹配引擎——`common.js` 的匹配语义是契约，改它属另一条线（本技能只使用、不修改）。
- **翻译资产只有字典**：任何「原文 → 中文」都写进 JSON 字典，脚本里不得硬编码翻译。
- 只收录**用户可见**文本（界面元素 / 读屏 / 命令行 / 报错）；用户不可见的日志文本不入字典。**例外（用户明确授权时）**：发给模型的输入文本（Copilot 提示词 / 冲突输入文档 / 仓库约束说明）也可收录——前提是保留全部输出契约（JSON 键、`"keep"` / `"delete"` 等取值、解析器依赖的字段），并走「行为验证」实测模型输出仍符合契约（实证：`c0333d8` 提示词中文化、`1db6fd1` 输入文档中文化）。
- 字典条目**译文不得为空串**（`buildEntries` 会抛「译文必须是非空字符串」），需要「消掉」某段英文时用单空格 `" "`。
- 只做**本地提交**：不 push / merge / 建 PR；显式 `git add <文件>`，禁 `-A` / `.`；提交信息不带任何 `Co-Authored-By` 类署名。
- 仓库开源：字典与脚本里不写绝对路径、机器名、凭据。

## 铁律（每条都是踩坑后的结论，别凭直觉）

1. **干跑在备份上，复查在产物上**——口径反过来必然得到假结论：
   - 收录前的**命中验证**必须跑在 `tmp/backup/<版本>/` 的官方原文上。拿 patched 产物干跑，英文早被替换掉了，**必然 0 命中**（假阴性）。
   - 打包后的**落地复查**必须跑在**安装目录的 patched 产物**上（`%LOCALAPPDATA%\GitHubDesktop\app-<版本>\resources\app\`）。在备份上数「原文还剩几处」，量出来的是原文原本有几处（假阳性）。
2. **探针一律写成 `tmp/probeNNN.cjs` 再 `node` 执行**，不用 `node -e`：bash 会吃掉 `${}`、反斜杠 Windows 路径与中文引号（症状：路径里的反斜杠被吞、`SyntaxError: Invalid regular expression`、变量莫名变成 `NaN`）。同理**不要在 shell 里拼中文 grep / 正则**，一律落成 `.cjs`。
3. **输出必须截断**：探针只打印前 N 条（`slice(0, 420)` / `LIMIT`）。一次 600KB 的输出会把上下文撑爆，后续全部走样。
4. **改字典 → 必须先 `restore` 再 `patch`**：`patch` 是原地替换，**不会**把已删条目的旧译文从产物里退出。删过或改过条目却直接重打，残留的失效译文继续生效。
5. **零命中 = 删键**：干跑后 0 命中的候选，要么键写错（含首尾空格 / 大小写 / 引号），要么已被整模板键覆盖——都从候选里剔除，不留「看起来对但没生效」的条目。冗余条目会让 `patch` 的「0 命中待核对」告警失去意义。
6. **一个桶一个提交**：按主题分批（错误提示 / 跨元素片段 / 菜单 / 表单标签…），每批走完 打包 → 验证 → 落地复查 → 提交 全链再开下一批。批次太大时一次会话会反复触发上下文压缩、证据链断裂。
7. **不靠人眼、也不只靠用户截图**：截图只作线索；结论以产物取证为准。用户给的截图可能**已过期**——先确认图里的英文在当前产物是否已归零，再决定要不要动。
8. **备份必须确为官方原版**：`locate` 的备份是「已存在则跳过」，污染备份会静默通过并让后续所有取证失真。核验口径：官方原版两个文件的汉字字符数为 **0**（3.6.5 实测：备份 0 / 0，汉化产物 599 / 15706）。

## 关键机制（口径错多半错在这里）

- **匹配是「逐字面量整串相等」，不做子串替换**。候选池按完整字面量提取，所以 `"sessions.setAdditionalPlugins"` 不会因为含 `"Add"` 被误伤。推论：**看起来危险的片段键往往安全**，判定要落到「这个字面量在代码里怎么用」，而不是「这段文字像什么」。
- **`stringLiterals(src)` 返回 `{content, start, end, template}`**：`start` / `end` 指向**引号内内容**（不含引号）——判断「字面量后面紧跟什么」时，post 串以**闭合引号**开头。模板字面量按**文本段**逐个收集（`template:false`），含插值时**额外**整段收集一份（含两侧反引号，`template:true`）供整模板键匹配。
- **替换优先级**：起点升序、同起点**长的优先**——整模板键覆盖其内部的文本段。
- **`applyDictInStrings(content, entries)` 期望「已剥离作用域前缀」的键**：传 `scopedEntries(entries, 'renderer.js')` 的结果，别直接把 `renderer.js|Enabled` 塞进去（会 0 命中）。返回 `{content, total, perKey}`。
- **`loadDict()` 返回的 Map 保留原样键**（含 `renderer.js|` 前缀），供统计 / 报告用。

## 三种改字典的手段

| 手段 | 键形态 | 何时用 |
| --- | --- | --- |
| 普通键 | `"原文": "译文"` | 字面量或模板文本段，整串相等即替换（如含尾随空格的 `"Fetch "`） |
| **作用域键** | `"<文件名>.js\|原文"` | 同一字面量在两个文件里语义不同。典型：`renderer.js\|en-US`（renderer 是相对时间语言、main 是拼写检查）、`renderer.js\|Enabled`（renderer 是表单 label、main 是 winston 的 `"is"+X+"Enabled"` 拼接） |
| **整模板键** | `` "`${…}…`": "`${…}中文…`" `` | 运行时拼接的文案（复数是函数拼出来的、动词由函数返回）；显示与逻辑**复用同一字面量**时用它覆盖外层模板，让内部片段不再被单独替换 |

## 任务 A：更新翻译（版本升级后更新汉化包）

官方更新后新的 `app-<新版本>/` 里是官方原版，汉化被覆盖；字典与版本强对应，必须为新版本建字典再重打。

**详程见 `references/版本升级.md`**，主干：`npm run locate`（定位 + 备份，并核验备份无汉字）→ 派生 `dictionaries/<新版本>/` → 在新版原文上全量干跑找出失效条目（整模板键因构建变量名变化几乎全部失效）→ 重建整模板键 → 补译新版新增文案（走任务 B）→ 打包验证 → 提交 `feat(dictionaries): 新增 <新版本> 字典（N 条）`。

## 任务 B：补充翻译

### 1. 取证

```bash
npm run scan --out tmp/scan.txt        # 读安装目录 renderer.js.map 里的官方源码，输出「源码有、字典没收录、产物里真实存在」的候选
npm run scan --out tmp/scan.txt --min-length 6   # 候选太少时放宽阈值
```

- 截图用视觉能力读（`mcp__cc-vision-hook__vision_describe_image`）；读不出时退回 `Read`（该工具可直接看图片）。
- 要定位「某条英文属于哪个字面量、出现在哪些位置」：写探针用 `stringLiterals` 在**产物**上枚举，打印命中位置与前后 60 字上下文——属性名（`label` / `title` / `ariaLabel` / `placeholder` / `okButtonText` / `description`）、`===` 比较、`.get(` 调用都是判定依据。
- `scan` 的候选里混着 `lib/` 与 `ui/dispatcher/` 的内部错误/日志文本（非 UI 漏译），按收录范围剔除。
- **扫描盲区**：React 多文本节点拼接（数字 + 短英文片段）不是单一字面量，`scan` 看不到——界面出现「2 changed files」这类中英混杂时，去产物里找该组件渲染函数（`renderFileHeader` 一类），用**整模板键**接管。

### 2. 判定能不能译

逐条过 `references/收录判定.md` 的四步检查。结论只有三种：**可译**（普通键）／**仅单文件可译**（作用域键）／**不可译**（保持英文，或改走整模板键覆盖外层模板）。

### 3. 干跑预演

把 `references/probe.cjs` 拷成 `tmp/probeNNN.cjs`，填 `CANDIDATES` 后执行（`MODE = 'dry'`）：在**备份原文**上预演，逐键报命中数与位置。

- **零命中的键一律剔除**（铁律 5）。
- 记下合计命中数——打包时 `npm run patch` 的输出必须与它**完全一致**，这是最有说服力的一致性证据。

### 4. 写入字典

保持既有格式：2 空格缩进、每行一条 `"原文": "译文",`、**末条无逗号**。条目多时用脚本做**字符串级**插入（读文件 → 定位末条 → 补逗号 → 追加），**不要** `JSON.parse` + `JSON.stringify` 重排（会把整文件 diff 搅乱）。

```bash
node -e "console.log(Object.keys(require('./dictionaries/<版本>/zh-CN.json')).length)"   # 写入前后各跑一次，确认条目数
```

### 5. 收尾

走「通用收尾」。

## 任务 C：纠正翻译问题

### 1. 定性与取证

| 现象 | 性质 | 取证 |
| --- | --- | --- |
| 界面中英混杂、该译没译 | 漏译 → 走任务 B | 探针枚举字面量 + `scan` |
| 术语不对 / 语序别扭 | 错译 | 产物定位 → 改字典值 |
| 功能异常（计数不对、拉取失败、进度条卡住、下拉选项错乱） | **译文破坏功能** | 能复现时以截图 / 日志取证；不能复现时在产物里找该字面量的**所有**出现位置，逐处看是否参与比较 / 查表 / 拼接 |
| **右键菜单等由运行时生成的文本一直是英文**（菜单标签、Electron 的 `role` 展开项） | 不是漏译，是**字典机制够不着**——产物里根本没有这个字面量 | 在产物里数该字面量：**0 处**即可定性（`scan` 也扫不出来，别反复找）。处置需注入代码（`scripts/inject/context-menu.js`），**超出本技能「只改字典」的边界**——要动先与用户确认，详见 AGENTS.md 架构一节 |
| `patch` 报「0 命中待核对」或 `verify` 报残留 | 失效 / 冗余条目 | 全量干跑列出 0 命中条目 |
| 产物里留着已删条目的旧译文 | 未重打 | 见铁律 4：`restore` 后才能退出 |

代码里找不到界面文案时，用 `renderer.js.map`（sourcemap 内嵌官方源码）反查出处。

### 2. 判定与处置

按 `references/收录判定.md` 判定，三种处置：

- **完全不可译** → **从字典删除该键**；
- **仅单文件语义冲突** → 改成**作用域键**（`renderer.js|原文`），另一文件保持英文；
- **显示与逻辑复用同一字面量** → 改**整模板键**覆盖外层模板（让内部片段不被单独替换）；覆盖不了时，满足「整体替换」条件（全部出现位置在同一文件、无跨进程 / 持久化 / 上报、比较两侧同源、配套插值模板收尾正确，实证 `"Rebase"` 34 处同值同改 → 「变基」，见 `references/收录判定.md`「整体替换」一节）可整体替换；否则保持英文，写进汇报的「有意保留」清单。

### 3. 收尾

走「通用收尾」。

## 通用收尾（三个任务共用）

```bash
npm run restore     # 本轮若有删除或修改条目，此步必做（铁律 4）
npm run patch       # 命中数应与干跑预期完全一致
npm run verify      # 版本一致 + 两文件语法通过 + 残留英文清零
```

**落地复查**：在 patched 产物上抽查（`references/probe.cjs` 的 `MODE = 'land'`）——原文残留归零 + 译文在位 + 变量占位 `${…}` 与转义保留。

```bash
git add dictionaries/<版本>/zh-CN.json          # 显式指定，禁 -A / .
git commit -m "fix(dictionaries): <一句话>（N → M 条）"
```

提交信息沿用仓库既有风格（如 `fix(dictionaries): 补译…（1801 → 1854 条）`、`fix(字典): 修复变更视图与冲突提示未汉化`），`fix` 类正文按「问题现象 → 原因分析 → 修改方案 → 涉及文件」组织——把「某字面量在哪个位置参与逻辑」写清楚，这是这类提交唯一有价值的证据。不带署名。

## 行为验证（改动了发给模型的文本时）

改动提示词 / 冲突输入文档 / 约束说明等**发给模型的文本**后，落地复查证明的只是「替换到位」，不等于「模型输出仍符合契约」——还要跑一次真实 Copilot 会话确认：

- 模板：`references/copilot-behavior-test.cjs`（拷到 `tmp/` 按需改 marker 与用例开关后执行）
- 做法：不另起炉灶，照 `copilot-store.ts` 的方式用**应用自带**的 Copilot 运行时（`GitHubDesktop.exe` 以 node 身份执行 `copilot/index.js`，SDK 在应用目录内）；系统提示词**从已打补丁的 renderer.js 里取**（测的就是装机产物里那一条）；token 从凭据管理器读（keytar，服务名 `GitHub - <endpoint>`），**全程不打印、不进仓库**；
- 断言：提交信息回复能 `JSON.parse` 且 `title` 非空；冲突解决回复的 `resolutions` / `summary` / `action`（`keep` / `delete`）符合契约、`resolvedContent` 无残留冲突标记；
- 代价与前置：**每条用例消耗 1 次 Copilot 请求**（模型 `auto`，约 6–7 秒）——跑之前先告知用户配额消耗；本机访问 GitHub 需走代理（`HTTPS_PROXY` / `HTTP_PROXY` 环境变量，见 AGENTS.md 已知坑）。

## 汇报模板

```markdown
## 本次改动
- 新增 N 条 / 删除 M 条 / 改写 K 条（字典 X → Y 条）
- 涉及文件：dictionaries/<版本>/zh-CN.json

## 验证
- 干跑预期命中 A 处 → 实际 patch 命中 A 处（一致）
- npm run verify：版本一致 ✓ / 语法通过 ✓ / 残留英文 <列出>
- 落地复查：<抽查了哪几条，结果>

## 有意保留（不译及原因）
- `"..."` —— <参与比较 / 协议常量 / 共用字面量 / 日志文本>

## 需要用户操作
- 重启 GitHub Desktop 才能看到新译文（磁盘产物已更新，运行中实例仍是旧内存代码）
```

## 可迁移性（这套打法不止用于 GitHub Desktop）

本技能是「**字典驱动的汉化补丁**」这一打法的 GitHub Desktop 实例化。换一个应用（同样没有官方 i18n 通道、界面文本硬编码在打包产物里的 Electron 应用）时，**需要替换的只有两样**：

1. **匹配引擎**——即本仓库 `scripts/common.js` 承担的"如何从产物里找出可替换的字面量区间"；
2. **路径约定**——字典目录、备份目录、安装目录探测（`dictionaries/<版本>/`、`tmp/backup/<版本>/`、`locate`）。

**照搬的部分**（与具体应用无关，是本技能真正的资产）：

- **三类键形态**：普通键 / 作用域键 / 整模板键，分别对应「字面量或模板文本段」「同一文本在两个文件里语义不同」「运行时拼接、或显示与逻辑复用同一字面量」；
- **「能不能译」的四步检查**（`references/收录判定.md`）：只用于显示 → 可译；有比较 / 查表 → 看两侧是否同源；被拼接成标识符 → 不可译或改作用域键；与外部系统对齐（协议常量、环境变量名、日志匹配串、CSS 属性值）→ 不可译；外加零步「产物里有没有这个字面量」——运行时生成的文案（Electron 菜单标签）字典够不着；
- **运行时文本的注入式处置**（`scripts/inject/context-menu.js`）：文本由运行时按 `role` 生成、产物里没有字面量时，注入一段代码把英文原文**造进产物**，再由同一次字典替换译掉——注入块只带英文、不带中文，字典仍是唯一翻译资产；
- **双口径取证**（干跑在原件、复查在产物）与 `references/probe.cjs` 探针模板；
- **三条工程约束**：字典是唯一翻译资产（脚本不内置翻译）、字典与版本强对应、改字典必先还原再重打。

## 任务跟踪

环境提供 `TodoWrite` / `Task*` 时用原生任务清单跟踪（完成一项勾一项、收尾核对无未勾项）；否则在对话内维护「事项 → 状态」文本清单。**批次之间不要并行改字典**——字典是单一文件，并发写会互相覆盖。
