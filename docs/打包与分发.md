# 打包与分发

把汉化工具分发给普通用户：使用者无需安装 Node.js、无需命令行，双击即用。两种形态——**单文件可执行**（中文菜单，本文件主线）与 **Electron 图形界面**（操作面板，见[下文](#图形界面gui产物)）。

- 给使用者：**使用教程见 [README「使用方式」](../README.md#使用方式)**——方式一是图形界面（GUI 操作面板）、方式二是现成的单文件产物、方式三是源码运行
- 给分发者：[单文件产物怎么构建](#给分发者怎么构建产物) · [图形界面产物怎么构建](#图形界面gui产物) · [跨平台构建](#跨平台构建)

## 给分发者：怎么构建产物

### 前置

- Node.js ≥ 20.12（用到 SEA 的 assets），**建议 ≥ 22.20**——更低版本缺少 `sea.getAssetKeys()`，产物仍能汉化，但菜单里列不出内嵌字典版本（构建时会告警）。构建机器上有对应平台的 Node 即可。
- 首次构建会通过 `npx` 拉取固定版本的 [postject](https://github.com/nodejs/postject)（仅构建期使用，不进产物）。

```bash
npm run build            # 产物输出到 dist/
npm run build -- --help  # 查看选项（--out <目录> / --name <文件名>）
```

构建流程（`scripts/build.js`）：

1. `bundle.js` 把 `scripts/` 合成单个自包含 `.js`（零依赖，不引入打包器）；
2. 生成 SEA 配置，把**最新版本**的字典（`dictionaries/<最新>/zh-CN.json`）内嵌为资源——内嵌只为「开箱即用」，更早版本用到时会自动联网拉取；
3. `node --experimental-sea-config` 生成 blob；
4. 复制当前 node 可执行文件作为产物基底；
5. postject 注入 blob → 产出 `dist/github-desktop-zh-cn-v<版本>-<平台>-<架构>[.exe]`，并自动跑一次 `--help` 自检。

产物约 83 MB（Windows x64 / Node 22），压缩为 zip 后约 1/3，分发时建议压缩。

### 命令行用法

产物同时是完整的命令行工具，行为与源码态脚本一致：

```bash
<产物> patch --dry-run            # 预览汉化命中统计，不写盘
<产物> patch                      # 汉化
<产物> restore                    # 还原官方原版
<产物> verify                     # 校验版本一致性、命中率与补丁后语法
<产物> locate                     # 定位安装目录并备份
<产物> scan                       # 未翻译文案自查
<产物> --help                     # 查看全部子命令
```

`--path <resources目录>` / `--version <版本>` 与源码态一致。

### 跨平台构建

产物**只能在构建平台运行**（Windows 构建 `.exe`、macOS 构建 Mach-O、Linux 构建 ELF）——基底是构建机上的 node 可执行文件，且 macOS 产物还必须在 macOS 上注入与签名。所以跨平台**没有交叉构建这条路**：只能每个平台各构建一次，所谓「交叉构建脚本」在这里不成立。

本仓库自带 `.github/workflows/build.yml`，用 GitHub Actions 的矩阵一次出全部平台产物（**推荐**，本机不必装任何环境）：

| 矩阵项 | 产物 |
| --- | --- |
| `windows-latest` | Windows x64 `.exe` |
| `macos-latest` | macOS arm64（Apple Silicon） |
| `macos-15-intel` | macOS Intel x64 |
| `ubuntu-latest` | Linux x64 |

矩阵同时构建**两类产物**（两个 job 并行，见下节）：单文件可执行（`build` job，Artifacts 名 `dist-<os>`）与 Electron 图形界面（`gui` job，Artifacts 名 `gui-<os>`）。发 Release 时两者一起作为附件。

两种用法：

- **只构建**：Actions 页面 →「构建与发布」→ Run workflow，产物在该次运行的 Artifacts 里；
- **构建并发布**：推一个与 `package.json` 版本一致的**注解 tag**，workflow 先校验版本、再构建，最后自动建 Release 并附上全部产物与 `SHA256SUMS`：

  ```bash
  git tag -a v0.1.0 -m "v0.1.0: 首个版本"   # 注解 tag；版本须与 package.json 一致
  git push origin main --follow-tags
  ```

  发版须**三处对齐**：`CHANGELOG.md` 顶部条目 / `package.json` 的 `version` / tag，任一不一致时 CI 在构建前就失败；Release 正文取自 `CHANGELOG.md` 对应段落（本地可用 `node scripts/changelog.js 0.1.0` 预览）。Release 由仓库 secret `RELEASE_TOKEN`（作者本人的 PAT）创建，署名即作者——完整发版流程与 secret 配置方法见 `AGENTS.md` 的「发版」一节。

需要 arm64 的 Linux / Windows 产物时，往 `build.yml` 的 `matrix.include` 里加 `ubuntu-24.04-arm` / `windows-11-arm` 即可，其余不用改。

其他做法：

1. **各平台各跑一次**：在 Windows / macOS / Linux 上分别 `npm run build`（单文件产物）与 `npm run dist`（GUI 产物）；
2. **虚拟机 / 容器**：在目标系统里构建。

### 图形界面（GUI）产物

命令行菜单是「先看提示再敲数字」，适合脚本化与排错；不想碰命令行的使用者用 **GUI 版本**——Electron 原生窗口，汉化 / 还原 / 选择安装位置 / 检查更新都是按钮，下方列出当前字典的全部条目（只读，可按中英文搜索），底部显示安装位置与进度。

```bash
npm install      # 首次：安装 Electron 与 electron-builder（devDependencies，不进产物逻辑）
npm run gui      # 开发态：直接开窗，用仓库里的字典与备份（数据根 = 仓库根）
npm run dist     # 打包 → dist/gui/（按当前平台；产物清单见下）
```

各平台的产物（`artifactName` 统一为 `<name>-v<版本>-<平台>-<架构>.<扩展名>`，平台词与单文件产物一致用 `darwin` / `win32` / `linux`）：

| 平台 | 直接分发的产物 | 中间目录 |
|---|---|---|
| Windows | NSIS 安装包（`…-win32-x64-setup.exe`）、**zip 免安装包**（`…-win32-x64.zip`） | `win-unpacked/` |
| macOS | dmg（`…-darwin-arm64.dmg` / `…-darwin-x64.dmg`）、zip | `mac/`、`mac-arm64/` |
| Linux | AppImage、deb | `linux-unpacked/` |

**分发不要用** electron-builder 的 portable 目标：portable 运行时会把自己解压到临时目录，`process.execPath` 指向临时位置，备份与 `config.json` 会跟着写进临时目录、退出后可能被清理。本仓库因此不配置该目标，免安装需求由 zip / dmg 满足。

macOS 产物**不做代码签名**（本仓库没有证书，`mac.identity: null`）：使用者首次打开需右键「打开」确认，或 `xattr -dr com.apple.quarantine "<应用路径>"`，否则 Gatekeeper 会直接拒绝。

GUI 与命令行**共用 `scripts/` 的全部逻辑**——定位 / 替换 / 备份 / 还原没有第二份实现，`gui/main.js` 直接 `require('../scripts/…')` 调业务。渲染进程无 Node 能力（`contextIsolation` + `sandbox`），字典表格只读，**UI 里不存在字典写盘通道**。

打包配置在 `electron-builder.yml`：

- `files`：`gui/` + `scripts/` + `package.json` 进 `resources/app.asar`（asar 内 `require` 正常）；
- `extraResources`：`dictionaries/` 进应用的 `resources/dictionaries`——`node:sea` 在 Electron 里不可用，字典不能像 SEA 产物那样内嵌；而**不能**放 exe 同级（`extraFiles`），因为 macOS 的数据根恒在用户数据目录（`.app` 包内写入会让签名失效、下次启动被 Gatekeeper 拒开）、Linux 的 AppImage 运行目录只读又取不到旁边那份。改由 `gui/main.js` 的 `seedBundledDicts()` 首次运行时把数据根里缺的版本复制过去（只补缺失，用户自己替换或在线更新过的字典不被覆盖），`dataRoot()/dictionaries` 的「外部字典优先」逻辑因此零改动命中；
- `directories.output: dist/gui`；NSIS 目标 `oneClick: false`（可选安装目录）、`perMachine: false`（装到用户目录，省掉 UAC）。

### GUI 产物的 CI 构建

`.github/workflows/build.yml` 的 `gui` job 与单文件产物的 `build` job 并行跑同一套四平台矩阵（Windows x64 / macOS arm64 / macOS x64 / Linux x64），`release` job 等两类产物都完成再建 Release，附件含全部平台产物与 `SHA256SUMS`。两个 job 都不做交叉构建——Electron 二进制与原生打包工具（`winCodeSign` / `nsis`）都是平台相关的。

CI 在境外，构建前会 `rm -f .npmrc` 去掉国内镜像，并用 `--config.electronDownload.mirror=…` 把 Electron 下载地址覆盖回官方源（yml 里固化的是 npmmirror）。

`dist` 脚本固定带 `--publish never`，**别去掉**：electron-builder 26 只要 `publish` 没显式指定就自己判定——检出 tag 时按 `onTag`、仅检测到 CI 时按 `onTagOrDraft`，随后在**四个平台各自构建全部跑完之后**才去找 `GH_TOKEN`，找不到就报 `GitHub Personal Access Token is not set` 并 exit 1。症状是「每个平台的 GUI job 都失败、且都失败在最后一步」，而本地怎么跑都成功（本地既非 CI 也不在 tag 上，这条分支不触发），很容易误判成打包配置坏了。本仓库的 Release 由 `gh release create` 创建、不走 electron-builder，所以显式关掉。要本地复现这个坑：`CI=true GITHUB_REF_TYPE=tag GITHUB_REF_NAME=v0.2.0 npm run dist`。

每平台构建后跑 `node build/check-gui-dist.js` 静态自检：应用包结构（`app.asar` 大小与必备文件清单）、内置字典、Windows 产物的 PE 子系统是否为 `2`（GUI，双击不弹控制台）、是否有可直接分发的产物文件。**运行态实测仍要在本地做**——CI runner 没有桌面会话，起不了窗口。

**构建期网络（镜像已固化在文件里，不必手动设环境变量）**：首次 `npm install` / `npm run dist` 要下载 Electron 二进制与 electron-builder 的 `winCodeSign` / `nsis` 工具包，直连 GitHub 很慢。`.npmrc` 里的 `electron_mirror` / `electron_builder_binaries_mirror` 会被 npm 转成 `npm_config_*` 传给子进程；Electron 二进制的下载地址还额外固化在 `electron-builder.yml` 的 `electronDownload.mirror`——electron-builder 取 Electron 走的是 `resolveAssetURL`，**不读** `ELECTRON_MIRROR` 环境变量，只能靠这个 yml 键。换镜像时两处一起改。

### 发布前检查清单

- [ ] `npm test` 全绿；
- [ ] `npm run patch -- --dry-run` 的合计命中数与字典版本预期一致；
- [ ] `npm run build` 自检通过；
- [ ] 在一台**干净机器**（无 Node.js）上双击产物，走一遍：指定位置 → 汉化 → 重启 GitHub Desktop 看中文 → 还原；
- [ ] 联网状态下点一次菜单 `5) 检查更新`：字典能拉到、工具自身能识别新版本（自更新会替换自身并重启，验证时可先只看提示）；
- [ ] 说明 SmartScreen / 杀软提示的处理方式（见上文），避免使用者以为是病毒；
- [ ] 如同时发布 GUI 产物：`npm run dist` 后先跑 `node build/check-gui-dist.js`（结构 / 内置字典 / Windows 子系统），再启动 zip 免安装包实测——确认**不出现控制台窗口**、窗口布局无截断，走一遍汉化 → 还原 → 再汉化，且数据根与备份落在**解压目录**（不是临时目录），状态栏显示与磁盘实际一致；
- [ ] 用 tag 发布时**三处对齐**：`CHANGELOG.md` 顶部条目、`package.json` 的 `version`、注解 tag（CI 会校验，不一致直接失败）。

## 常见问题

**Q：产物为什么这么大？**
A：内含完整运行时。单文件产物内嵌 Node.js（约 80 MB，压缩后约 25–30 MB）；GUI 产物内含 Electron，体积高一个量级（Windows 实测：zip 146 MB、NSIS 安装包 106 MB——NSIS 压缩率更高），各平台略有差异。这样使用者无需安装任何环境。

**Q：能做成安装包吗？**
A：单文件产物本身免安装（删文件即卸载），没必要再包一层。GUI 形态倒是有 NSIS 安装包（`npm run dist` 产出），给习惯「装进开始菜单」的使用者用——它只写常规的卸载项，备份与 `config.json` 仍在应用目录里。

**Q：字典更新了，要重新发产物吗？**
A：不必。使用者那边有两条自动路径：菜单第 `5) 检查更新` 会拉取当前版本的最新字典；本地没有对应版本字典时（如旧版本产物遇到新版本 GitHub Desktop）工具会**自动到远程仓库下载**。此外把新字典放到数据目录的 `dictionaries\<版本>\` 下即可覆盖内嵌字典。重新打包只是让「开箱即用」的字典更新。GUI 产物同理——字典内置在应用内（`resources/dictionaries`），首次运行时播种到数据根，不重打包也能被用户替换。

**Q：能在没装 GitHub Desktop 的机器上用吗？**
A：能运行、能看到菜单，但没有可汉化的目标；菜单会提示「未找到」并引导手动指定路径。GUI 同理——状态栏提示「请点击「选择」指定安装位置」，「选择」按钮可用。

**Q：源码方式还能用吗？**
A：能，且完全不受影响——`npm run patch` / `restore` / `verify` / `scan` 行为不变。打包产物只是同一套脚本的另一种运行形态（数据根目录由仓库根改为可执行文件所在目录）；`npm run gui` 属开发态，数据根仍是仓库根。
