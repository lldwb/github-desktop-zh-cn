# 打包与分发

把汉化工具打包成**单文件可执行**分发给普通用户：使用者无需安装 Node.js、无需命令行，双击即用。

- 给使用者：[下载后怎么用](#给使用者下载后怎么用)
- 给分发者：[怎么构建产物](#给分发者怎么构建产物) · [跨平台构建](#跨平台构建)

## 给使用者：下载后怎么用

### 1. 运行

双击产物（Windows 为 `github-desktop-zh-cn-v<版本>-win32-x64.exe`），出现中文菜单：

```
 GitHub Desktop 汉化工具 v0.1.0
────────────────────────────────────────────────────────────────
 安装位置：C:\Users\<用户名>\AppData\Local\GitHubDesktop\app-3.6.6\resources\app
 应用版本：3.6.6
 字典版本：3.6.6（1861 条）
 当前状态：未汉化（官方原版）
 备份目录：（无——首次汉化时自动生成）
────────────────────────────────────────────────────────────────
 1) 汉化 GitHub Desktop       2) 还原官方原版
 3) 详细信息                  4) 指定安装位置
 0) 退出
 请选择：
```

| 选项 | 作用 |
| --- | --- |
| `1) 汉化` | 按当前版本字典汉化；**原文件会先自动备份**，可随时还原 |
| `2) 还原` | 还原官方原版（覆盖已汉化文件） |
| `3) 详细信息` | 显示数据目录、配置文件、字典来源、备份位置 |
| `4) 指定安装位置` | 自动探测失败或装在非默认位置时手动指定（可直接把文件夹拖进窗口） |

汉化完成后**重启 GitHub Desktop** 才能看到中文界面（运行中的实例仍是旧界面）。

### 2. 会自动找到 GitHub Desktop 吗

Windows 下会自动探测 `%LOCALAPPDATA%\GitHubDesktop` 下的**最新版本**目录。

macOS / Linux 或自定义安装位置：选 `4) 指定安装位置`，把 `resources` 目录路径粘进去（也可直接拖拽文件夹）。指定过一次会被记住。

- macOS 例：`/Applications/GitHub Desktop.app/Contents/Resources`
- Linux 例：`/usr/lib/github-desktop/resources`

### 3. 版本必须对应

字典与 GitHub Desktop 版本**强对应**，错配可能导致应用无法启动。工具已内置保护：

- 安装版本没有对应字典时（例如官方已更新到尚未发布字典的新版本），菜单会提示「无 3.6.7 对应字典（现有：3.6.5 / 3.6.6）」并拒绝汉化；
- GitHub Desktop 更新到新版本后，需要等对应版本的字典发布，再重新运行本工具。

### 4. 文件放在哪里

产物把「数据目录」定在**可执行文件所在目录**（放在 `D:\工具\` 里，数据就在 `D:\工具\`）：

```
D:\工具\
├── github-desktop-zh-cn-v0.1.0-win32-x64.exe   # 产物本体（自带字典）
├── config.json                                  # 记住的安装位置（用过「指定安装位置」才生成）
└── tmp\backup\<版本>\                           # 官方原版备份（首次汉化时生成）
```

放在**不可写**的位置（如 `C:\Program Files`）时，数据目录自动回退到用户数据目录：

- Windows：`%APPDATA%\github-desktop-zh-cn`
- macOS：`~/Library/Application Support/github-desktop-zh-cn`
- Linux：`$XDG_DATA_HOME`（默认 `~/.local/share/github-desktop-zh-cn`）

### 5. 换成自己的字典

产物已内嵌发布时的字典，**外部字典优先于内嵌字典**。想改译文：在数据目录下建 `dictionaries\<版本>\zh-CN.json`（格式见 `dictionaries/README.md`），重新运行工具即可生效——不必重新打包。

### 6. 系统提示怎么处理

- **Windows SmartScreen**：首次运行可能出现「Windows 已保护你的电脑」。产物未做代码签名（开源项目通常不做），点「更多信息」→「仍要运行」即可。
- **杀毒软件误报**：Node.js 打包的单文件程序（SEA）偶被启发式引擎误报，属已知误报类型；可加白名单，或改用源码方式运行。
- **macOS**：产物未签名时右键 →「打开」，或执行 `xattr -dr com.apple.quarantine <产物>`；用 `npm run build` 在 macOS 上构建会自动做 ad-hoc 签名（`codesign --sign -`）。
- **汉化后 GitHub Desktop 本体**：替换的是官方安装目录内的 `main.js` / `renderer.js`，Windows 下可能触发 SmartScreen 提示，不影响功能。

### 7. 卸载 / 还原

选 `2) 还原官方原版` 还原，然后删掉产物与数据目录即可——不写注册表、不装服务、不改系统设置。

## 给分发者：怎么构建产物

### 前置

- Node.js ≥ 20.12（用到 SEA 的 assets），**建议 ≥ 22.20**——更低版本缺少 `sea.getAssetKeys()`，产物仍能汉化，但菜单里列不出内嵌字典版本（构建时会告警）。构建机器上有对应平台的 Node 即可。
- 首次构建会通过 `npx` 拉取固定版本的 [postject](https://github.com/nodejs/postject)（仅构建期使用，不进产物）。

```bash
npm run build            # 产物输出到 dist/
npm run build -- --help  # 查看选项（--out <目录> / --name <文件名>）
```

构建流程（`scripts/build.js`）：

1. `bundle.js` 把 `scripts/` 合成单个自包含 `.js`（零依赖，不引入打包器）；
2. 生成 SEA 配置，把 `dictionaries/*/zh-CN.json` **全部内嵌**为资源；
3. `node --experimental-sea-config` 生成 blob；
4. 复制当前 node 可执行文件作为产物基底；
5. postject 注入 blob → 产出 `dist/github-desktop-zh-cn-v<版本>-<平台>-<架构>[.exe]`，并自动跑一次 `--help` 自检。

产物约 83 MB（Windows x64 / Node 22），压缩为 zip 后约 1/3，分发时建议压缩。

### 命令行用法

产物同时是完整的命令行工具，行为与源码态脚本一致：

```bash
<产物> patch --dry-run            # 预览汉化命中统计，不写盘
<产物> patch                      # 汉化
<产物> restore                    # 还原官方原版
<产物> verify                     # 校验版本一致性、命中率与补丁后语法
<产物> locate                     # 定位安装目录并备份
<产物> scan                       # 未翻译文案自查
<产物> --help                     # 查看全部子命令
```

`--path <resources目录>` / `--version <版本>` 与源码态一致。

### 跨平台构建

产物**只能在构建平台运行**（Windows 构建 `.exe`、macOS 构建 Mach-O、Linux 构建 ELF）——基底是构建机上的 node 可执行文件，且 macOS 产物还必须在 macOS 上注入与签名。所以跨平台**没有交叉构建这条路**：只能每个平台各构建一次，所谓「交叉构建脚本」在这里不成立。

本仓库自带 `.github/workflows/build.yml`，用 GitHub Actions 的矩阵一次出全部平台产物（**推荐**，本机不必装任何环境）：

| 矩阵项 | 产物 |
| --- | --- |
| `windows-latest` | Windows x64 `.exe` |
| `macos-latest` | macOS arm64（Apple Silicon） |
| `macos-15-intel` | macOS Intel x64 |
| `ubuntu-latest` | Linux x64 |

两种用法：

- **只构建**：Actions 页面 →「构建与发布」→ Run workflow，产物在该次运行的 Artifacts 里；
- **构建并发布**：推一个与 `package.json` 版本一致的**注解 tag**，workflow 先校验版本、再构建，最后自动建 Release 并附上全部产物与 `SHA256SUMS`：

  ```bash
  git tag -a v0.1.0 -m "v0.1.0: 首个版本"   # 注解 tag；版本须与 package.json 一致
  git push origin main --follow-tags
  ```

  发版须**三处对齐**：`CHANGELOG.md` 顶部条目 / `package.json` 的 `version` / tag，任一不一致时 CI 在构建前就失败；Release 正文取自 `CHANGELOG.md` 对应段落（本地可用 `node scripts/changelog.js 0.1.0` 预览）。完整发版流程见 `AGENTS.md` 的「发版」一节。

需要 arm64 的 Linux / Windows 产物时，往 `build.yml` 的 `matrix.include` 里加 `ubuntu-24.04-arm` / `windows-11-arm` 即可，其余不用改。

其他做法：

1. **各平台各跑一次**：在 Windows / macOS / Linux 上分别 `npm run build`；
2. **虚拟机 / 容器**：在目标系统里构建。

### 发布前检查清单

- [ ] `npm test` 全绿；
- [ ] `npm run patch -- --dry-run` 的合计命中数与字典版本预期一致；
- [ ] `npm run build` 自检通过；
- [ ] 在一台**干净机器**（无 Node.js）上双击产物，走一遍：指定位置 → 汉化 → 重启 GitHub Desktop 看中文 → 还原；
- [ ] 说明 SmartScreen / 杀软提示的处理方式（见上文），避免使用者以为是病毒；
- [ ] 用 tag 发布时**三处对齐**：`CHANGELOG.md` 顶部条目、`package.json` 的 `version`、注解 tag（CI 会校验，不一致直接失败）。

## 常见问题

**Q：产物为什么这么大？**
A：内含完整 Node.js 运行时（约 80 MB）与全部字典。这样使用者无需安装任何环境。压缩后约 25–30 MB。

**Q：能做成安装包吗？**
A：可以，但没必要——产物是单文件、免安装，删文件即卸载。若确需安装包，用 Inno Setup（Windows）/ `create-dmg`（macOS）等对产物再包一层即可，本仓库不提供。

**Q：字典更新了，要重新发产物吗？**
A：不必。把新字典放到数据目录的 `dictionaries\<版本>\` 下即可覆盖内嵌字典；重新打包只是让「开箱即用」的字典更新。

**Q：能在没装 GitHub Desktop 的机器上用吗？**
A：能运行、能看到菜单，但没有可汉化的目标；菜单会提示「未找到」并引导手动指定路径。

**Q：源码方式还能用吗？**
A：能，且完全不受影响——`npm run patch` / `restore` / `verify` / `scan` 行为不变。打包产物只是同一套脚本的另一种运行形态（数据根目录由仓库根改为可执行文件所在目录）。
