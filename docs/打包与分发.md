# 打包与分发

把汉化工具分发给普通用户：使用者无需安装 Node.js、无需命令行，双击即用。两种形态——**单文件可执行**（中文菜单，本文件主线）与 **Electron 图形界面**（操作面板，见[下文](#图形界面gui产物)）。

- 给使用者：**使用教程见 [README「使用方式」](../README.md#使用方式)**——方式一是图形界面（GUI 操作面板）、方式二是现成的单文件产物、方式三是源码运行
- 给分发者：[单文件产物怎么构建](#给分发者怎么构建产物) · [图形界面产物怎么构建](#图形界面gui产物) · [跨平台构建](#跨平台构建)

## 给分发者：怎么构建产物

### 前置

- Node.js ≥ 20.12（用到 SEA 的 assets），**建议 ≥ 22.20**——更低版本缺少 `sea.getAssetKeys()`，产物仍能汉化，但菜单里列不出内嵌字典版本（构建时会告警）。构建机器上有对应平台的 Node 即可。
- 首次构建会通过 `npx` 拉取固定版本的 [postject](https://github.com/nodejs/postject)（仅构建期使用，不进产物）。

```bash
npm run build            # 产物输出到 dist/
npm run build -- --help  # 查看选项（--out <目录> / --name <文件名>）
```

构建流程（`scripts/build.js`）：

1. `bundle.js` 把 `scripts/` 合成单个自包含 `.js`（零依赖，不引入打包器）；
2. 生成 SEA 配置，把**最新版本**的字典（`dictionaries/<最新>/zh-CN.json`）内嵌为资源——内嵌只为「开箱即用」，更早版本用到时会自动联网拉取；
3. `node --experimental-sea-config` 生成 blob；
4. 复制当前 node 可执行文件作为产物基底；
5. postject 注入 blob → 产出 `dist/github-desktop-zh-cn-cli-v<版本>-<平台>-<架构>[.exe|.bin]`（Windows 用 `.exe`，macOS / Linux 用 `.bin`——`cli` 是通道词，图形界面那套是 `gui`），并自动跑一次 `--help` 自检。

产物约 83 MB（Windows x64 / Node 22），压缩为 zip 后约 1/3，分发时建议压缩。

### 命令行用法

产物同时是完整的命令行工具，行为与源码态脚本一致：

```bash
<产物> patch --dry-run            # 预览汉化命中统计，不写盘
<产物> patch                      # 汉化
<产物> restore                    # 还原官方原版
<产物> verify                     # 校验版本一致性、命中率与补丁后语法
<产物> locate                     # 定位安装目录并备份
<产物> scan                       # 未翻译文案自查
<产物> --help                     # 查看全部子命令
```

`--path <resources目录>` / `--version <版本>` 与源码态一致。

### 跨平台构建

产物**只能在构建平台运行**（Windows 构建 `.exe`、macOS 构建 Mach-O、Linux 构建 ELF）——基底是构建机上的 node 可执行文件，且 macOS 产物还必须在 macOS 上注入与签名。所以跨平台**没有交叉构建这条路**：只能每个平台各构建一次，所谓「交叉构建脚本」在这里不成立。

本仓库自带 `.github/workflows/build.yml`，用 GitHub Actions 的矩阵一次出全部平台产物（**推荐**，本机不必装任何环境）：

| 矩阵项 | 产物 |
| --- | --- |
| `windows-latest` | Windows x64 `.exe` |
| `macos-latest` | macOS arm64（Apple Silicon） |
| `macos-15-intel` | macOS Intel x64 |
| `ubuntu-latest` | Linux x64 |

矩阵同时构建**两类产物**（两个 job 并行，见下节）：单文件可执行（`build` job，Artifacts 名 `dist-<os>`）与 Electron 图形界面（`gui` job，Artifacts 名 `gui-<os>`）。发 Release 时两者一起作为附件。

两种用法：

- **只构建**：Actions 页面 →「构建与发布」→ Run workflow，产物在该次运行的 Artifacts 里；
- **构建并发布**：推一个与 `package.json` 版本一致的**注解 tag**，workflow 先校验版本、再构建，最后自动建 Release 并附上全部产物与 `SHA256SUMS`：

  ```bash
  git tag -a v0.1.0 -m "v0.1.0: 首个版本"   # 注解 tag；版本须与 package.json 一致
  git push origin main --follow-tags
  ```

  发版须**三处对齐**：`CHANGELOG.md` 顶部条目 / `package.json` 的 `version` / tag，任一不一致时 CI 在构建前就失败；Release 正文取自 `CHANGELOG.md` 对应段落（本地可用 `node scripts/changelog.js 0.1.0` 预览）。Release 由仓库 secret `RELEASE_TOKEN`（作者本人的 PAT）创建，署名即作者——完整发版流程与 secret 配置方法见 `AGENTS.md` 的「发版」一节。

需要 arm64 的 Linux / Windows 产物时，往 `build.yml` 的 `matrix.include` 里加 `ubuntu-24.04-arm` / `windows-11-arm` 即可，其余不用改。

其他做法：

1. **各平台各跑一次**：在 Windows / macOS / Linux 上分别 `npm run build`（单文件产物）与 `npm run dist`（GUI 产物）；
2. **虚拟机 / 容器**：在目标系统里构建。

### 图形界面（GUI）产物

命令行菜单是「先看提示再敲数字」，适合脚本化与排错；不想碰命令行的使用者用 **GUI 版本**——Electron 原生窗口，汉化 / 还原 / 选择安装位置 / 检查更新都是按钮，下方列出当前字典的全部条目（只读，可按中英文搜索），底部显示安装位置与进度。

```bash
npm install      # 首次：安装 Electron 与 electron-builder（devDependencies，不进产物逻辑）
npm run gui      # 开发态：直接开窗，用仓库里的字典与备份（数据根 = 仓库根）
npm run dist     # 打包 → dist/gui/（按当前平台；产物清单见下）
```

各平台的产物（`artifactName` 统一为 `<name>-gui-v<版本>-<平台>-<架构>.<扩展名>`——通道词 `gui` 紧跟项目名，与单文件产物的 `cli` 成对；平台词用 `darwin` / `win32` / `linux`。架构词随目标走：Windows / macOS 是 `x64` / `arm64`，Linux 由 electron-builder 按各自规范给名——AppImage 是 `x86_64`、deb 是 `amd64`）：

| 平台 | 直接分发的产物 | 中间目录 |
|---|---|---|
| Windows | NSIS 安装包（`…-gui-v<版本>-win32-x64-setup.exe`）、**zip 免安装包**（`…-gui-v<版本>-win32-x64.zip`） | `win-unpacked/` |
| macOS | dmg（`…-gui-v<版本>-darwin-arm64.dmg` / `…-gui-v<版本>-darwin-x64.dmg`）、zip（架构词同上） | `mac/`、`mac-arm64/` |
| Linux | AppImage（`…-gui-v<版本>-linux-x86_64.AppImage`）、deb（`…-gui-v<版本>-linux-amd64.deb`） | `linux-unpacked/` |

**分发不要用** electron-builder 的 portable 目标：portable 运行时会把自己解压到临时目录，`process.execPath` 指向临时位置，备份与 `config.json` 会跟着写进临时目录、退出后可能被清理。本仓库因此不配置该目标，免安装需求由 zip / dmg 满足。

macOS 产物**不做代码签名**（本仓库没有证书，`mac.identity: null`）：使用者首次打开需右键「打开」确认，或 `xattr -dr com.apple.quarantine "<应用路径>"`，否则 Gatekeeper 会直接拒绝。

产物有两条自查路径：`node build/check-gui-dist.js`（静态自检：结构 / 依赖文件 / 语言包裁剪 / 体积）与产物自带的 `--smoke-test`（真起一次窗口，核对界面与一次真实 IPC 往返，打印 `SMOKE_OK` 并以 0 退出，失败打 `SMOKE_FAIL` 并退出 1）——后者每次 CI 构建都会跑，本地也能用同一条命令自查。

GUI 与命令行**共用 `scripts/` 的全部逻辑**——定位 / 替换 / 备份 / 还原没有第二份实现，`gui/main.js` 直接 `require('../scripts/…')` 调业务。渲染进程无 Node 能力（`contextIsolation` + `sandbox`），字典表格只读，**UI 里不存在字典写盘通道**。

打包配置在 `electron-builder.yml`：

- `files`：`gui/` + `scripts/` + `package.json` 进 `resources/app.asar`（asar 内 `require` 正常）；
- `extraResources`：`dictionaries/` 进应用的 `resources/dictionaries`——`node:sea` 在 Electron 里不可用，字典不能像 SEA 产物那样内嵌；而**不能**放 exe 同级（`extraFiles`），因为 macOS 的数据根恒在用户数据目录（`.app` 包内写入会让签名失效、下次启动被 Gatekeeper 拒开）、Linux 的 AppImage 运行目录只读又取不到旁边那份。改由 `gui/main.js` 的 `seedBundledDicts()` 首次运行时把数据根里缺的版本复制过去（只补缺失，用户自己替换或在线更新过的字典不被覆盖），`dataRoot()/dictionaries` 的「外部字典优先」逻辑因此零改动命中；
- `directories.output: dist/gui`；NSIS 目标 `oneClick: false`（可选安装目录）、`perMachine: false`（装到用户目录，省掉 UAC）；
- `electronLanguages: [en-US, zh-CN, zh_CN]` 与 `afterPack: build/after-pack.js`：运行时裁剪——语言包只留中英两个，软渲染与 WebGPU 编译器打包后删掉。三平台各删各的：Windows 的 `vk_swiftshader.dll` / `dxcompiler.dll`、macOS 的 `libvk_swiftshader.dylib`、Linux 的 `libvk_swiftshader.so`（外加各自的 `vk_swiftshader_icd.json`）；ffmpeg 与 Linux 的 `libvulkan.so.1` 刻意保留（语义上不该碰 / 影响面比实现大）。理由与实测数字见「常见问题」第一条。`zh_CN`（下划线）是给 macOS 的：它的语言目录叫 `zh_CN.lproj`，而 electron-builder 的匹配规则是「相等或前缀 + 分隔符」且两边都转小写，`zh-CN` 与 `zh_CN` 互不相认——少了这条 mac 产物只剩英文；这个写法在 Windows / Linux（`zh-CN.pak`）匹配不到任何文件，无副作用。

### GUI 产物的 CI 构建

`.github/workflows/build.yml` 的 `gui` job 与单文件产物的 `build` job 并行跑同一套四平台矩阵（Windows x64 / macOS arm64 / macOS x64 / Linux x64），`release` job 等两类产物都完成再建 Release，附件含全部平台产物与 `SHA256SUMS`。两个 job 都不做交叉构建——Electron 二进制与原生打包工具（`winCodeSign` / `nsis`）都是平台相关的。

CI 在境外，构建前会 `rm -f .npmrc` 去掉国内镜像，并用 `--config.electronDownload.mirror=…` 把 Electron 下载地址覆盖回官方源（yml 里固化的是 npmmirror）。

`dist` 脚本固定带 `--publish never`，**别去掉**：electron-builder 26 只要 `publish` 没显式指定就自己判定——检出 tag 时按 `onTag`、仅检测到 CI 时按 `onTagOrDraft`，随后在**四个平台各自构建全部跑完之后**才去找 `GH_TOKEN`，找不到就报 `GitHub Personal Access Token is not set` 并 exit 1。症状是「每个平台的 GUI job 都失败、且都失败在最后一步」，而本地怎么跑都成功（本地既非 CI 也不在 tag 上，这条分支不触发），很容易误判成打包配置坏了。本仓库的 Release 由 `gh release create` 创建、不走 electron-builder，所以显式关掉。要本地复现这个坑：`CI=true GITHUB_REF_TYPE=tag GITHUB_REF_NAME=v0.2.0 npm run dist`。

每平台构建后跑 `node build/check-gui-dist.js` 静态自检：应用包结构（`app.asar` 大小与必备文件清单）、内置字典、Windows 产物的 PE 子系统是否为 `2`（GUI，双击不弹控制台）、语言包是否裁到中英两个（Windows / Linux 查 `locales/*.pak`，macOS 的语言目录是 `.lproj` 且分布在应用级与 Framework 的 Resources 两处，自检合并核对：缺中文或混进第三种语言都报错）、可直接分发的产物文件在不在**且名字是否走 `…-gui-v<版本>-…` 命名**；同时把每个产物的体积打进日志（超 100 MB 的额外打一条 `::warning::`，判据见「Gitee 镜像发版」）——跑一次 CI 就能看到四平台的实际体积，不必下载附件。

**接着跑产物启动冒烟**（静态自检看不出「删掉的运行时组件是不是启动必需的」）：产物带 `--smoke-test` 真起一次，核对窗口内容区尺寸、界面按钮数与一次**真实 IPC 往返**（判据、输出格式与超时见 `gui/main.js` 顶部注释），打印 `SMOKE_OK` 且退出码 0 才算过，冒烟不过就不上传产物。三平台各一套起法：Windows 用 `Start-Process -Wait -RedirectStandardOutput`（GUI 子系统程序从 PowerShell 的 `&` 调用既不等待也不捕获输出）、macOS 直接执行 `.app/Contents/MacOS/` 里的可执行文件（绕开 LaunchServices，输出与退出码都是自己的）、Linux 用 `xvfb-run`（runner 没有显示；容器里 Chromium 沙箱与 `/dev/shm` 都不合用，`--no-sandbox` 与 `--disable-dev-shm-usage` 都关掉）。**四个 runner 都没有 GPU**，所以这轮冒烟同时是「软渲染组件删掉后还有没有回退路径」的验证（输出里带 GPU 合成 / WebGL / Vulkan 状态，裁剪前后可直接对照）。本地同一条命令即可自查：`dist/gui/win-unpacked/GitHubDesktopZhTool.exe --smoke-test`。

**功能级实测仍要在本地做**——汉化 / 还原 / 字典同步要有真的 GitHub Desktop 安装目录才验得了。

**构建期网络（镜像已固化在文件里，不必手动设环境变量）**：首次 `npm install` / `npm run dist` 要下载 Electron 二进制与 electron-builder 的 `winCodeSign` / `nsis` 工具包，直连 GitHub 很慢。`.npmrc` 里的 `electron_mirror` / `electron_builder_binaries_mirror` 会被 npm 转成 `npm_config_*` 传给子进程；Electron 二进制的下载地址还额外固化在 `electron-builder.yml` 的 `electronDownload.mirror`——electron-builder 取 Electron 走的是 `resolveAssetURL`，**不读** `ELECTRON_MIRROR` 环境变量，只能靠这个 yml 键。换镜像时两处一起改。

### 定时字典（`dict-auto.yml`）

另一个工作流，与构建无关：**每天定时看 GitHub Desktop 有没有新版本，有就自动产出该版本的字典**（取官方产物 → 以历史字典为锚核对每条键在新产物里的形态 → 官方新增的界面文案走 AI 翻译 → 经 `dict-edit` 事务写入 → 推断组名 → 干跑校验）。已有字典的版本默认跳过（幂等，不白烧 tokens）；要重跑用 `workflow_dispatch` 的 `on_exist` 下拉选 `diff`（照常产出但**全程不写盘**，只报逐键差异）或 `overwrite`（产出后整体覆盖，任一步失败则恢复原内容）。

**AI 服务配置**（`translateBatch` 走 OpenAI 兼容协议，三项都必配，缺任一项工作流在开始前就失败并说明原因）：

| 名称 | 位置 | 说明 |
|---|---|---|
| `AI_BASE_URL` | Secrets | 网关地址（指向自建网关，不公开）。**必须是带 `http(s)://` 前缀的绝对地址**——预检只判这个前缀，脚本发请求前另按 URL 语法校验一次，并会拦下**看不见的字符**（不换行空格、零宽空格、串内空格——这类值语法上过得去，只是请求会打到别的路径上 404，报错里给出码点）；两处都只报形态、不回显值 |
| `AI_API_KEY` | Secrets | 凭据 |
| `AI_MODEL` | Variables | 模型名——不暴露基础设施信息，且日志里看得见，排查「配置到底生效没有」时省事 |
| `AI_REASONING_EFFORT` | Variables | 思考强度，默认 `low`；**开高档必须同时放大 `AI_TIMEOUT_SEC`**，否则每批超时后退化成逐条重试，更慢且请求数翻倍 |
| `AI_TIMEOUT_SEC` | Variables | 单次请求超时秒数，默认 120 |

**分处两页是有意的**：公开仓库的 Actions 日志人人可看，`AI_BASE_URL` 与 `AI_API_KEY` 会被打成 `***`，而模型名与两个参数放 Variables 是为了在日志里能看见。

**失败要能查**：注解与 step summary 人人可看，**job 日志只有仓库管理员能取**（匿名拉日志得 403），所以失败原因（地址错 / 鉴权失败 / 超时……）会随结论一起写进注解、汇总与提交信息正文，其中的网关地址、**主机名**与凭据已抹成 `***`。配错 `AI_BASE_URL` 的典型症状是「未译 100% 超过上限」——结论离原因很远，故两处校验都尽量把它拦在前面；查地址时按上面的形态逐项核对（首尾空格这类「值本身可用、只是日志脱敏可能失效」的情况只打 `::warning::`，不拦）。

### Gitee 镜像发版

Gitee 上的仓库由镜像自动同步 commit / 分支 / tag，**但发行版不在同步范围内**——所以 tag 推上去后 Gitee 那边仍是空的。`release` job 末尾的「发布到 Gitee」步骤负责补上：按 tag 探测 → 没有就创建，正文取 CHANGELOG 段落并追加一段指向 GitHub Release 的下载指引。它排在 GitHub Release 发布**之后**——Gitee 是镜像渠道，出问题不该影响权威源的成果；失败只让 job 标红，已发布的 GitHub Release 原样保留。

**只发正文、不传附件**：Gitee 的配额放不下这些产物——附件**单文件上限 100 MB**（GUI 产物里只有 Windows 的 NSIS 安装包 90.7 MB 达标，zip 免安装包 123.6 MB 仍超，其余平台 GUI 产物同量级——最接近的 mac arm64 dmg 也有 104.0 MB），**单仓库附件总容量 1 GB**（四平台产物合计 GB 级，裁剪后仍放不下）；这两项在 SaaS 各档位都一样（社区版 100 MB / 1 GB，企业版单文件同样是 100 MB），只有私有化部署才提供定制配额。所以 Gitee 侧没有产物，**发行版正文里那段链接就是唯一的下载入口**，少写它使用者只会看到一个空壳。

**也别指望把构建搬到 Gitee 上来绕开配额**：Gitee Go 的构建插件（Maven / Gradle / Ant / Golang / Node.js / PHP / Python / GCC）基础镜像全是 CentOS 7.6 / 8.3 与 Ubuntu 20.04，**没有 Windows、没有 macOS runner**——而本仓库 13 个产物里 10 个必须在各自平台原生构建（见上文「跨平台」）。Gitee Go 的免费额度也只有 500 分钟/月，构建与发版留在 GitHub Actions。

需要 `GITEE_TOKEN`（Actions secrets，**可选**）：Gitee → 设置 → 私人令牌（<https://gitee.com/profile/personal_access_tokens>），勾 `projects` 权限。**缺它不阻断发布**——`check-version` 里会打一条 `::warning::` 说明本次不会同步到 Gitee，那一步直接跳过。

两个 Gitee 特有的行为（照搬 GitHub 的判据会出错）：按 tag 查发行版时它用 **`200` + 字面量 `null`** 表示不存在，不是 `404`；发行版对象**没有 `html_url`** 字段，要按 tag 自己拼。

使用者侧还有一条兜底：`scripts/update.js` 的「检查更新」在 GitHub 取不到时退回 Gitee 的 `/releases/latest`。**它只够告知版本号**——Gitee 上不放产物附件，实际下载仍须走 GitHub。

### Secrets 与 Variables 清单（一次配齐）

| 名称 | 位置 | 用途 | 缺失时 |
|---|---|---|---|
| `RELEASE_TOKEN` | Secrets | 建 / 改 Release——**必须**是作者本人的 PAT，内置 token 建出来的署名是 `github-actions[bot]` 且事后改不了 | `check-version` 与 `release` 都会失败并说明配置方法 |
| `AI_BASE_URL` / `AI_API_KEY` | Secrets | 定时字典的翻译服务 | `dict-auto.yml` 开始前失败 |
| `AI_MODEL` / `AI_REASONING_EFFORT` / `AI_TIMEOUT_SEC` | Variables | 同上 | 只缺 `AI_MODEL` 时跑到翻译那步才报 |

> 这几项的值本身不会被打印出来（`AI_BASE_URL` / `AI_API_KEY` 是 Secret，日志里显示成 `***`）。配错时的症状是「未译 100% 超过上限」——若汇总与注解里出现这句，先按 `AI_BASE_URL` 的形态核对一遍（前缀、引号、空格/全角字符）。
| `GITEE_TOKEN` | Secrets | 同步发行版到 Gitee | 打 `::warning::` 后跳过，不阻断 |

`RELEASE_TOKEN` 的权限与仓库范围（Fine-grained token 怎么建）见 `AGENTS.md`「发版」一节。

## 常见问题

**Q：产物为什么这么大？**
A：内含完整运行时。单文件产物内嵌 Node.js（约 80 MB，压缩后约 25–30 MB）；GUI 产物内含 Electron，体积高一个量级——Electron 二进制解压后 368 MB，压进安装包后四平台实测（裁剪后）：Windows zip 123.6 MB / NSIS 安装包 90.7 MB、macOS dmg 104.0 MB（arm64）/ 112.1 MB（x64，zip 同量级）、Linux deb 91.1 MB / AppImage 115.2 MB——NSIS 与 deb 用 LZMA / xz，比 zip 的 deflate 压得狠，同一份内容更小。其中 70–80 MB 是打包时**已经裁掉的**：55 个 Chromium 语言包只留中英两个（`electron-builder.yml` 的 `electronLanguages`），软渲染与 WebGPU 编译器去掉（`build/after-pack.js`，三平台各删各的）——裁掉后界面与功能不受影响：CI 四平台的**产物启动冒烟**（`--smoke-test`）在**没有 GPU 的 runner** 上全部通过，GPU 合成退回软件路径、界面照常加载；Windows 另有本机实机验证（汉化 / 还原 / 字典同步无异常）。但**再往下就动不得了**：余下的大件是 Chromium 内核本身，删了应用起不来。**各平台的裁剪收益取决于官方发行包里该组件的实际体积**：同样 55 个语言，Windows / macOS 版各约 48 MB 而 Linux 版只有 8.6 MB，所以 Linux 只瘦 2 MB 出头；软渲染那块 macOS arm64 是 15.8 MB（压缩后 6.3，各平台里最大的一块），Windows 5.3（2.1）、macOS x64 与 Linux 各 4.4 MB 上下（压缩后 1.7）——arm64 与 x64 差 3.6 倍是官方发行包本身的差异，不是配置漏了哪个架构。zip 免安装包受 deflate 算法限制，123.6 MB 已是压缩极限（主程序单文件就占压缩后体积的 83%）；要进 100 MB 以内只能改成「引导器 + 首次运行下载」形态，跨平台各写一套、用户下载总量反而更大，与收益不成比例。这样使用者无需安装任何环境。

**Q：能做成安装包吗？**
A：单文件产物本身免安装（删文件即卸载），没必要再包一层。GUI 形态倒是有 NSIS 安装包（`npm run dist` 产出），给习惯「装进开始菜单」的使用者用——它只写常规的卸载项，备份与 `config.json` 仍在应用目录里。

**Q：字典更新了，要重新发产物吗？**
A：不必。使用者那边有两条自动路径：菜单第 `5) 检查更新` 会拉取当前版本的最新字典；本地没有对应版本字典时（如旧版本产物遇到新版本 GitHub Desktop）工具会**自动到远程仓库下载**。此外把新字典放到数据目录的 `dictionaries\<版本>\` 下即可覆盖内嵌字典。重新打包只是让「开箱即用」的字典更新。GUI 产物同理——字典内置在应用内（`resources/dictionaries`），首次运行时播种到数据根，不重打包也能被用户替换。

**Q：能在没装 GitHub Desktop 的机器上用吗？**
A：能运行、能看到菜单，但没有可汉化的目标；菜单会提示「未找到」并引导手动指定路径。GUI 同理——状态栏提示「请点击「选择」指定安装位置」，「选择」按钮可用。

**Q：源码方式还能用吗？**
A：能，且完全不受影响——`npm run patch` / `restore` / `verify` / `scan` 行为不变。打包产物只是同一套脚本的另一种运行形态（数据根目录由仓库根改为可执行文件所在目录）；`npm run gui` 属开发态，数据根仍是仓库根。
